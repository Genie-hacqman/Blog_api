# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This is a Node.js/Express blog API using MySQL via Sequelize. It implements auth under `/api/auth` (register, login, refresh, logout, logout-all, me, verify-email, resend-verification, forgot/reset/change-password), user profiles under `/api/users` (public `GET /:username` and `/:username/posts`; the signed-in user's `PATCH|DELETE /me`, `PUT|DELETE /me/avatar`, `POST /me/become-author`; `/me` routes are declared before `/:username`), image uploads at `/api/media`, admin endpoints under `/api/admin` (role changes, audit log), and post CRUD under `/api/posts` (create supports an optional `Idempotency-Key` header via `middleware/idempotency.js`). Posts move through seven statuses (`draft`, `pending_review`, `scheduled`, `published`, `rejected`, `archived`, `private`) driven by one table in `policies/postWorkflow.js`; authors submit and editors/admins approve or reject (`REQUIRE_POST_REVIEW=false` lets authors publish directly). Published posts are public: `GET /api/posts` (previews, newest-published first), `GET /api/posts/:id` and `GET /api/posts/slug/:slug` (no login needed; a bad token is still a 401). Everything else about a post belongs to its author, apart from the review and moderation states editors can see; anything a viewer may not see is a 404, never a 403. Public URLs use slugs (`/blog/<slug>`), generated from the title and frozen at first publication. Each post keeps a revision history (list, compare, restore). A post has at most one category (editors manage them: `/api/categories`) and up to five tags (authors create them while writing; editors rename or delete: `/api/tags`); `GET /api/posts` filters by `?category=<slug>` and `?tag=<slug>`, and `GET /api/search?q=` searches published posts. Every response uses one envelope: `{ success: true, data, meta? }` on success (e.g. `data: { post }`, list endpoints put `pagination` in `meta`) and `{ success: false, error: { code, message, details? } }` on failure. `GET /health` reports liveness plus a database check. Users have a `role` (`user` < `author` < `editor` < `admin`; see `config/roles.js`) and a `status` (`active`/`suspended`/`deleted`). New sign-ups are unverified `user`s; creating a post needs `post:create` (author+) and, while `REQUIRE_VERIFIED_EMAIL` is on, a verified email. New resources should follow the existing layering described below.

The React + Vite frontend lives in a separate sibling repo, `../Blog-frontend`, and talks to this API over CORS.

## Commands

- `npm run dev` — start with nodemon (auto-reload), used for local development.
- `npm start` — start with plain `node server.js`.
- `npm run migrate` / `npm run migrate:down` / `npm run migrate:status` — apply, revert (one step) or list schema migrations (`scripts/migrate.js`). The dev server applies pending migrations itself (`AUTO_MIGRATE` defaults to on in development only); in production a pending migration stops the boot, so run `npm run migrate` as a deploy step.
- `npm run lint` — oxlint (same linter as the frontend).
- `npm run admin:promote -- <email>` — promote an existing account to admin (the only way to create the first admin; audited with a null actor).
- `npm test` — integration tests via node's built-in test runner + `supertest`, in `tests/`. Requires a `blog_db_test` MySQL database (`CREATE DATABASE blog_db_test;`); the script passes `DB_NAME=blog_db_test` inline, which wins over `.env` because `dotenv.config()` does not overwrite already-set vars. `resetDatabase()` in `tests/helpers.js` refuses to run unless `DB_HOST` is `localhost`/`127.0.0.1` and `DB_NAME` contains `test`, because `.env` may point at real data (including the deployed Aiven database); pass local connection vars inline, e.g. `DB_HOST=localhost DB_PORT=3306 DB_USER=root DB_PASSWORD=... npm test`. `--test-concurrency=1` is required, since `node --test` otherwise runs files in parallel processes that would reset the shared test database out from under each other.
- Tests set `NODE_ENV=test`, which makes the rate limiters in `middleware/rateLimiter.js` skip (5 logins / 15 min cannot support a suite, and the window does not reset between runs). The limiters themselves are therefore covered by manual `request.http` checks, not automated tests.
- `tests/helpers.js` builds the schema by running the migrations (`migrator.up()`, a no-op once applied), then truncates every table except `SequelizeMeta` with foreign key checks off (on one connection, since the setting is per-connection). Tests therefore exercise the same schema production runs. Unit tests that need no database live in `tests/unit/`.
- CI is `.github/workflows/ci.yml` (MySQL service, lint, tests). Node 22+ is required (`node --test` glob support).
- Ad-hoc endpoint testing is done via `request.http` (VS Code REST Client format).

## Environment

Config is loaded and validated once, in `config/env.js` (dotenv + a Zod schema). Import `env` from there instead of reading `process.env`; a missing or invalid variable stops the boot with a message naming the variable (never its value). Variables:
- `NODE_ENV` — `development` (default), `test` or `production`. Production requires a `JWT_SECRET` of 32+ characters.
- `PORT` — server port (defaults to 3030 if unset).
- `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT` (defaults to 3306) — MySQL connection details passed straight into `new Sequelize(...)`.
- `JWT_SECRET` — used to sign/verify JWTs in `services/userService.js` and `middleware/authMiddleware.js`.
- `CLIENT_ORIGIN` — comma-separated browser origins allowed by CORS in `app.js` (defaults to `http://localhost:5173`, the Vite dev server).
- `TRUST_PROXY` — number of reverse proxies in front of the app (default `0`). Set it behind a host's proxy, or the rate limiters key every client to the proxy's IP.
- `LOG_LEVEL` (default `info`, `silent` in tests) and `AUTO_MIGRATE` (see Commands) are optional.
- `STORAGE_PROVIDER` — `local` (dev: folder `STORAGE_LOCAL_DIR`, served at `/media`), `memory` (tests) or `s3` (any S3-compatible bucket, e.g. Cloudflare R2; required in production, together with `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` and `STORAGE_PUBLIC_URL`, the bucket's public domain that image URLs are built from).
- `APP_URL` — frontend base URL used in emailed links (required in production). `EMAIL_PROVIDER` is `console` (dev: prints emails to the log), `memory` (tests) or `smtp` (required in production; needs `SMTP_HOST`, plus `SMTP_PORT/USER/PASSWORD/SECURE`, `EMAIL_FROM`).
- `SEARCH_PROVIDER` (only `mysql` for now) selects the search engine.
- `REDIS_URL` (optional; a secret, never logged), `QUEUE_PROVIDER` (`inline` | `bullmq`, defaults to bullmq when `REDIS_URL` is set and to inline in tests), `QUEUE_PREFIX` (default `blog`) and `WORKER_ENABLED` (default on) configure the job queue. Tests run the BullMQ suite only when `TEST_REDIS_URL` is set (e.g. `redis://127.0.0.1:6379/15`; each test uses its own key prefix and removes it).
- `REQUIRE_POST_REVIEW` (default `true`) makes authors submit posts for an editor's approval; `SCHEDULER_ENABLED` (default on, off in tests) and `SCHEDULER_INTERVAL_SECONDS` (default 60) control the job that publishes scheduled posts.
- `SEO_ENABLED` (default on; off answers 404 to robots.txt, sitemaps, feeds and snapshots), `SITE_NAME`, `SITE_TAGLINE`, `SITE_DESCRIPTION` (the publication's name in titles, feeds and previews).
- `REQUIRE_VERIFIED_EMAIL` (default `true`) gates post creation on a verified email; `COOKIE_SAMESITE` (`lax` default) and `COOKIE_SECURE` (default on in production) configure the refresh cookie.

Keep `.env.example` in sync when adding new required env vars.

## Architecture

The codebase follows a strict layered flow for each resource: **routes → middleware → controller → service → repository → Sequelize model**. Each layer has one job, and new features (like posts) should be added by mirroring this same set of files per resource (e.g. `postRoutes.js`, `postController.js`, `postService.js`, `postRepository.js`, `database/models/postModel.js`, `schemas/postSchemas.js`).

- **`app.js`** wires up the Express app: request logging, `helmet()`, JSON body parsing (256 KB limit), `cors()`, `/health`, feature routers under resource path prefixes (e.g. `/api/users`), then the 404 and error handlers.
- **`server.js`** is the entry point: calls `sequelize.authenticate()` before starting the HTTP listener (so the process fails fast if the DB is unreachable), applies or verifies migrations, starts `app.js`, and shuts down gracefully on SIGTERM/SIGINT.
- **`config/`** holds `env.js` (validated environment) and `logger.js` (pino, with `authorization`/`cookie`/`password`/`token` redacted). Log through the logger (or `req.log`), never `console.*`, and never log secrets.
- **Errors:** services throw the `AppError` subclasses in `utils/AppError.js` (`NotFoundError`, `ForbiddenError`, `ConflictError`, ...), which carry an HTTP status and a machine-readable `code`. `middleware/errorHandler.js` is the only place that turns errors into responses; anything that is not an `AppError` is logged and returned as a generic `INTERNAL_ERROR` with no message or stack. Controllers have no try/catch (Express 5 forwards rejected promises) and respond with `sendSuccess()` from `utils/response.js`.
- **`routes/`** wires an Express router, attaching `validate(schema)` and `authenticate` middleware in front of controller functions. Routes themselves contain no logic.
- **`middleware/userValidation.js`** exports a single higher-order `validate(schema)` middleware that runs a Zod schema's `safeParse` against `req.body`, replacing `req.body` with the parsed/coerced data on success or passing a `ValidationError` (message = first Zod issue, `details.issues` = all of them) to the error handler on failure. Reuse this pattern (`validate(schema)`) for any new resource rather than writing bespoke validation middleware.
- **Sessions and tokens.** Login issues a 15-minute access JWT (HS256, `iss`/`aud` pinned, `sub` = user id, `sid` = session id) returned in the body, and an opaque rotating refresh token in an `HttpOnly` cookie (`refresh_token`, `Path=/api/auth`). Refresh tokens are stored only as SHA-256 hashes in `refresh_tokens`; rows sharing a `familyId` are one login session. Rotation revokes the old row and links it to the new one; a rotated token replayed after a 10 s grace window (multi-tab race) revokes the whole family and is audited. Constants live in `config/auth.js`; token helpers in `utils/tokens.js`.
- **`middleware/authMiddleware.js`** implements `authenticate`: verifies the access token, loads the user from the DB (so role/status changes apply immediately), requires `status = active` and a live session (`sid` family with an unrevoked, unexpired token), then sets `req.user = { id, username, email, role, emailVerified }` and `req.sid`. Controllers and services must read role from `req.user`, never from the token. There is no in-memory revocation store any more; logout, logout-all, password change/reset and suspension end sessions in the database.
- **Authorization** has two layers, both server-side: `middleware/authorize.js` (`requirePermission('post:create')`, `requireVerifiedEmail`) for coarse role checks, and `policies/*` (e.g. `postPolicy.js`) for per-resource rules applied in services. A resource the caller may not even see (another user's draft) is answered with 404, not 403. Add a permission to `config/roles.js` in the same change that checks it. Writes on owned resources include the owner in the SQL `where`.
- **`middleware/cookieGuard.js`** protects the two endpoints that read the refresh cookie (`/refresh`, `/logout`): they require `X-Requested-With: fetch` and, if present, an `Origin` in `CLIENT_ORIGIN`.
- **Passwords** (`utils/hash.js`): argon2id; legacy bcrypt hashes verify and are re-hashed on the next login. Passwords are never trimmed (8 to 128 chars). Unknown emails still run a dummy hash. 10 consecutive failures lock an account for 15 minutes (`failedLoginCount`/`lockedUntil`); per-IP limiters sit in front (`middleware/rateLimiter.js`, per-process memory until Redis arrives).
- **Email** goes through `providers/email` (`getEmailProvider().send(...)`; console/memory/smtp) via `services/emailService.js`, which never throws and never logs message bodies. Verify/reset links use single-use hashed tokens in `user_tokens`. Emails are sent without awaiting the provider.
- **Post lifecycle.** `policies/postWorkflow.js` is the single source of truth for who may move a post from one status to another (`TRANSITIONS[from][to]` = a rule on user and post); `evaluateTransition` returns 404 for a post the user cannot see, 409 `INVALID_TRANSITION`, or 403 (`REVIEW_REQUIRED` when an author skips review). Status changes happen only through `POST /api/posts/:id/status` (`services/postStatusService.js`): the row is locked, the rule is checked, the write is conditional on the status that was checked, and the audit row commits with it. `PATCH /api/posts/:id` edits content only (title, content, excerpt, slug); it cannot change status, author or dates, and posts waiting for review, scheduled or archived are locked (409 `POST_LOCKED`). Visibility, edit and history rules are in `policies/postPolicy.js`. To add a status or move, change the table and its exhaustive test in `tests/unit/postWorkflow.test.js`.
- **Slugs, excerpts, revisions.** Slugs come from `utils/slug.js` (`slugify`, numbered on collision, random suffix when several requests collide; retried on unique violations and deadlocks) and are frozen at first publication (`SLUG_LOCKED`). `excerpt` and `readingTime` are stored on write (`utils/text.js`), so lists never load bodies. `services/postRevisionService.js` records a revision after every content change inside the same transaction; bursts of saves by the same author on unpublished posts merge into one revision, edits to published posts are each kept, at most 100 are kept per post, restoring creates a new revision. Comparison uses the `diff` package.
- **Categories, tags, search.** Categories are a nullable `Posts.categoryId`; tags are many-to-many through `post_tags` (composite primary key: no duplicates). Slugs are the public addresses; renaming a category or tag never changes its slug. Tag names are validated and merged by `utils/taxonomy.js` (`prepareTags`: letters, digits, spaces, hyphens; same slug = same tag); tags are created by `ensureTags` in `services/tagService.js` **outside** the post transaction on purpose (shared vocabulary must be visible across transactions), and a post's tags are attached to responses with one query via `attachTags` — always call it *after* the transaction commits, because it reads on another connection. Search goes `routes -> searchService -> providers/search (getSearchProvider) -> repositories/searchRepository.js`: the engine returns ranked post ids, `searchService` re-loads them and keeps only published posts, so a stale external index cannot leak anything. The MySQL engine uses two FULLTEXT indexes (title; excerpt+content), `MATCH ... AGAINST` in natural-language mode with every value bound as a parameter, and `utils/searchQuery.js` strips query syntax before the engine sees the text. Words under 3 characters are not indexed by InnoDB, so a query of only such words falls back to an escaped `LIKE` on the title. The body index is on `excerpt` + `contentText` (the plain text of the post), never on the HTML.
- **Rich content.** `Posts.content` is **sanitized HTML** produced by the editor; `Posts.contentText` is the plain text derived from it (what search, excerpts, reading time and the empty check use). HTML enters the system only through `sanitizeContent()` in `utils/richText.js` (allowlist: `p br h2 h3 h4 strong em s code pre blockquote ul ol li hr a img`; links http/https/mailto with a forced `rel="noopener noreferrer nofollow ugc"`; `code[class]` only as `language-*`; h1/h5/h6 are mapped to h2/h4; depth capped). Never store, return or render post HTML that did not pass through it, and never add `dangerouslySetInnerHTML`-style output of anything else. Text with no tags is accepted and wrapped into paragraphs (API clients). The one service that prepares a body is `services/postContentService.js` (`prepareContent`): sanitize, derive text, enforce limits (200,000 chars of HTML, 50,000 of text, 30 images, nesting 12) and require every `<img src>` to be one of **the author's own live inline uploads** (`INVALID_IMAGE` otherwise; a restored revision drops images that are gone instead of failing). `htmlToText`/`htmlToDiffText`/`htmlToPlainText`/`extractImageSrcs` in the same util read HTML back; `utils/text.js` `autoExcerpt`/`readingTimeOf` are given the plain text, not the HTML. A post's inline images are tracked in `post_media` and its cover in `Posts.coverMediaId` (+ `coverAlt`; cover must be the owner's `cover` upload). Saving values that are already stored changes nothing (no `updatedAt` bump, no revision), which autosave relies on; an optional `expectedUpdatedAt` on PATCH answers `409 EDIT_CONFLICT` if the post was saved since (resolution is one second, the column's). Revisions store the HTML and are compared as one line per block.
- **Comments, likes, bookmarks, follows.** Comments (`services/commentService.js`, `policies/commentPolicy.js`) are **plain text** (1 to 2,000 characters; control and bidirectional-override characters are stripped by `cleanBody`), never HTML, and must be shown as text. One level of replies: a reply's parent must be a live top-level comment of the same post. Top-level comments list newest first, replies oldest first, both paginated. Deletion is soft (`deletedAt`, body wiped): a deleted comment with live replies stays as a placeholder (`deleted: true`, no body, no author), one without disappears from lists. The author, the **post's author** and editors/admins (`comment:moderate`) may delete; deleting someone else's comment is audited (`comment.deleted_by_other`, metadata `as: post_author|moderator`, no text). Writing needs `comment:create` and a verified email, an hourly per-user quota (`config/engagement.js`) and `commentRateLimiter`; `Idempotency-Key` is honoured. **Comments, likes and bookmarks exist only on published posts**: any other status answers 404 for everyone (the rows stay and come back on republication). Likes (`PUT|DELETE /api/posts/:id/like`), bookmarks (`.../bookmark`) and follows (`PUT|DELETE /api/users/:username/follow`) are idempotent link-table rows with composite primary keys (`INSERT IGNORE`); `follows` also has a database CHECK against self-follows, which is why its foreign keys are `RESTRICT` (MySQL refuses a CHECK on cascading keys). Counts are computed, never stored: `attachPostData(posts)` in `services/engagementService.js` (tags + `likeCount` + `commentCount`, two grouped queries per page) replaces `attachTags` at every list/detail site, and must also be called after commit; `attachViewerState` adds `liked`/`bookmarked` on the two detail endpoints only. `GET /api/posts/feed` and `/bookmarks` (`services/feedService.js`) are declared before `/:id`. Account deletion removes the person's likes, bookmarks and follows (both ways) and wipes their comments. Phase 8 notifications hook in at the single place each event happens (`createComment`, `follow`, `likePost`).
- **Queue and notifications.** Background work goes through `providers/queue` (`getQueue().add(name, data)`): `inline` runs jobs in this process with the same retry rules (used when `REDIS_URL` is unset and always in tests, where `await getQueue().idle()` / `settleJobs()` in `tests/helpers.js` waits for them), `bullmq` uses Redis (chosen automatically when `REDIS_URL` is set; queues `notifications`, `emails`, `maintenance` in `config/queues.js`; the producer fails fast when Redis is down, workers are started by `startWorker()` unless `WORKER_ENABLED=false` and a separate `npm run worker` does it). A new job needs a name in `config/queues.js` and a handler in `jobs/handlers.js`. **Jobs carry ids and numbers only, never text or secrets** (Redis keeps them), and the worker recomputes recipients and content from the database. Security-critical emails (verify, reset) deliberately do NOT use the queue (their tokens would sit in Redis). Events are published with `void publishEvent({...})` from `services/notificationService.js` **after** the transaction commits (it never throws and never waits: a queue outage must not fail a request; the event is logged and lost). `handleEvent` (job `notify`) turns an event into `notifications` rows: one per recipient, unique `dedupeKey` (a retried job is harmless), skipping the actor and inactive accounts, honouring `notification_preferences` (a row exists if either channel is on; `inApp: false` rows are not shown in the inbox). `handleEmail` (job `notification-email`) sends only to verified addresses, at most 20 per person per hour, after atomically claiming `emailedAt` (so a retry or a second worker never sends twice; a failed send releases the claim and the queue retries). Notifications store ids; the inbox is built on read (`describe`) and **drops anything the recipient may no longer see** (`canViewPost`, deleted comments), and only the newest rejection notification of a story carries the reason. Emails carry a signed unsubscribe link (`utils/unsubscribeToken.js`, its own audience) and `List-Unsubscribe` headers; `POST /api/notifications/unsubscribe` is POST-only and public. Add a notification kind in `config/notifications.js`, an event case in `handleEvent`, the sentence in `emailContent`, and the frontend sentence; `CLAUDE.md` Phase 9+ features can reuse `publishEvent`.
- **Moderation and admin.** Readers (verified email) report a comment, a published story or a person once per target (`POST /api/reports`, unique `(reporterId, targetKey)`, `targetKey` like `comment:12`; 10 per hour; hidden things are 404, never described). **Reports never act on their own.** Editors and admins work the queue (`/api/moderation/reports`): one entry per reported target with its count and reasons, resolved as one decision (`resolveReport` closes every open report about the target in one transaction). Reports about **people are admin-only** (`reportTypesFor` in `policies/reportPolicy.js`; editors get 404 for them). Actions: `dismiss` (no note), `remove` (comment), `unpublish` (story), `suspend` (person); all but dismiss need a note. The queue reuses the existing rules rather than re-implementing them: `deleteWithin` (commentService) and `moveStatus` (postStatusService) run inside the report transaction, and `suspendWithin` (adminService) too. Taking down someone else's published story (to draft or archived) now **requires a reason**. When a comment or story is removed by someone else the author gets `comment_removed` / `post_unpublished` (event `content_removed`; the moderator's note is read by the worker from the audit row, job data stays ids only; `describe` does not hide a removal notice just because the comment is gone). **Suspension** (`POST /api/admin/users/:id/suspend`, admins only, reason required): sets `status`, `suspendedAt`, `suspendedReason`, revokes refresh tokens, audits, then emails the person directly (not through the queue); the per-request status check ends access tokens at once; login says why only after the password was right; self-suspension is refused and active admins are locked in the transaction so two admins cannot suspend each other into zero; scheduled stories of non-active authors are skipped by `findDueScheduledPosts`. Content stays up when its author is suspended. `GET /api/admin/stats` is counts only (analytics are a later phase). Exactly one of `reports.postId/commentId/targetUserId` is set and matches `targetType`: kept by the service, because MySQL refuses a CHECK on columns whose foreign keys cascade.
- **Analytics (reading statistics).** Collected by the browser, not by API reads: the public story page sends `POST /api/analytics/view` once and `POST /api/analytics/reading` when it is left (always answered `204` whatever was decided, so the answer reveals nothing; the counting happens after the response in `services/analyticsService.js`, tracked by `trackAnalytics` so tests can `await settleJobs()`). **Privacy is the design**: nothing identifying is stored. A visitor is `visitorHash(ip, userAgent, day)` (`utils/visitor.js`): a truncated HMAC whose key is derived from `JWT_SECRET` and the UTC date, so it changes daily and cannot be linked across days; it lives in `post_visitors` for two days (job `purge-analytics`, daily) and nothing else holds an address, a browser string, an account id or a cookie. `Do Not Track` / `Sec-GPC` visitors are counted as a view with no code. Referrers are reduced to a hostname (`(direct)`, `(internal)`, `(other)`; at most 50 distinct per story per day). Counting rules: only published stories, never the author's own visits, no robots (`looksLikeBot`), a visitor's repeat view counts again only after 30 minutes, a reader's reading report counts once, and a **read** needs 75% depth plus 40% of the reading time (clamped to 10 to 60 seconds). Counters are changed with single `x = x + n` statements (never read-modify-write). **"Visitors" are per day and are summed over a range**, so one person on three days counts three times; the interface says so. `readCount` is the column name because `reads` is a reserved word in MySQL (quote it as `` `reads` `` when it is an alias). Authors read their own stories' numbers (`analytics:read_own`; another author's story is 404), admins read everything (`analytics:read_all`, `/api/admin/analytics`). `utils/clock.js` is the single source of "now" for analytics and can be pinned in tests (`setNowForTests`). `ANALYTICS_ENABLED=false` stops collection.
- **SEO (search engines and link previews).** The frontend is a client-side app, so crawlers that do not run JavaScript (Slack, WhatsApp, Facebook, X, LinkedIn...) would see an empty page. `routes/seoRoutes.js` (mounted at the root of `app.js`, behind `SEO_ENABLED` and `seoRateLimiter`) serves, from `services/seoService.js`: `/robots.txt`, `/sitemap.xml` (index), `/sitemap-pages.xml` (front page + sections, topics and **active** authors that have a published story), `/sitemap-posts-:n.xml` (published stories, `SITEMAP_CHUNK` = 5,000 per file; a file out of range is 404), RSS feeds `/feed.xml` and `/feed/{author,category,tag}/<name>.xml` (30 newest, sanitized body in `content:encoded`), and the **crawler snapshots** `/api/seo/{home,blog/:slug,u/:username,category/:slug,tag/:slug}`: complete plain HTML pages (`views/snapshot.js`: title, description, canonical, Open Graph, Twitter, `article:*`, JSON-LD, the same text a reader sees, no scripts but the JSON-LD data block, no styles). The frontend host sends known crawler user agents there with a `vercel.json` rewrite (contract in the frontend README), everyone else gets the app. Visibility is exactly the public API's: a published story is visible whoever its author is today (suspended or deleted), a profile only for an **active** account; everything else (draft, archived, unknown slug, past the last page) is the same real `404` HTML page with `noindex`, which never says why. A section, topic or profile with nothing published still answers but is `noindex,follow`. Every interpolated value goes through `escapeHtml` / `escapeXml` / `jsonLdScript` (`utils/seoHtml.js`, `utils/xml.js`; `jsonLdScript` escapes `<`, `>`, `&`, U+2028/9 so a title cannot close the script), story HTML is run through `sanitizeContent` again on the way out, relative storage URLs become absolute with `absoluteUrl` (APP_URL), and no email address or account id appears in any output. All addresses are built from `APP_URL`; `SITE_NAME`, `SITE_TAGLINE`, `SITE_DESCRIPTION` name the publication. Queries stay constant as the list grows (`repositories/seoRepository.js` reads only ids, slugs and dates; feeds fetch bodies with one extra query). Add a public page type by adding a snapshot in `seoService`, a route here, and the frontend `useSeo` call; add a private path to `DISALLOWED_PATHS` in `config/seo.js`.
- **Jobs.** `jobs/scheduler.js` is the in-process timer (`server.js` starts and stops it); `jobs/sweepOrphanMedia.js` (every 6 hours from the same timer) removes cover/inline images older than 24 hours that no post uses; `jobs/publishScheduled.js` publishes due scheduled posts, safe to run from several instances (`SKIP LOCKED`, conditional update, deadlock retry via `retryOnDeadlock` in `database/transaction.js`). Tests call `publishDuePosts()` directly.
- **Database note:** the connection sets the `+FOUND_ROWS` flag, so an UPDATE reports rows *matched*, not rows changed; code can treat a count of 0 as "no such row". Sequelize returns 0 for an update with no values, so skip the write when there is nothing to change.
- **Media** goes through `providers/storage` (`getStorage().put/delete/publicUrl`; local/memory/s3) and one pipeline, `services/mediaService.js` + `utils/image.js`: multer memory upload (5 MB), type sniffed from the bytes with `file-type` (JPEG/PNG/WebP/GIF only, never SVG), full decode + re-encode to WebP with `sharp` (24 MP cap, EXIF/GPS stripped, resized per purpose in `config/media.js`), server-generated key `u/<ownerId>/<uuid>.webp` (the client filename is never used; every provider also refuses keys that do not match that shape), row in `media`. Never trust `file.mimetype` or `file.originalname`. Deleting a media row is a soft delete plus a best-effort file delete. Profile photos only via `PUT /api/users/me/avatar`; `POST /api/media` is for post images (`cover`/`inline`). 100 uploads per user per day. `DELETE /api/media/:id` answers `409 MEDIA_IN_USE` while a post still shows the image.
- **Profiles:** public profile data is built field by field in `services/profileService.js` (username, bio, avatar, social links, join date, post count; no email, names or role). `PATCH /api/users/me` is `.strict()` (only `bio` and `socialLinks`); social links are https URLs whose host must match the platform (`schemas/profileSchemas.js`, `config/profile.js`). New usernames are 3 to 30 of `[A-Za-z0-9_]` and not reserved; older usernames may not match. Author objects on posts come from `utils/author.js` (`toAuthor`), which renders deleted accounts as "Deleted user".
- **Account deletion** (`services/accountService.js`): needs the password, anonymizes the row (email/username/names/bio/links/avatar), revokes sessions, deletes drafts, keeps published posts, all in one transaction with an audit row. The row is never hard-deleted (posts reference it).
- **Audit log:** `services/auditService.js` `recordAudit()` writes append-only rows to `audit_logs` (metadata is stripped of anything credential-shaped). Pass `{ transaction }` for privileged changes so the row commits with the change; without one it is best-effort. Use `withTransaction` from `database/transaction.js` for multi-step writes.
- **`schemas/`** holds Zod object schemas per resource, used both by `validate()` middleware and directly in services where needed.
- **`controllers/`** are thin: call into a service and send the result with `sendSuccess()`. They contain no business logic or direct DB access.
- **`services/`** hold business logic: uniqueness checks, password hashing (`bcryptjs`), JWT signing, and shaping the sanitized user object returned to clients (`sanitizeUser`, which strips the password hash). Services signal failures by throwing `AppError`s (e.g. `new UnauthorizedError("Invalid email or password")` → 401); controllers never inspect error messages.
- **`repositories/`** are the only layer that talks to Sequelize models directly (`findByPk`, `findOne`, `create`, etc.). Services never import a model directly — they go through a repository.
- **`database/dbconnection.js`** creates the shared `Sequelize` instance (MySQL dialect). **`database/models/`** defines Sequelize models only; models never call `sync()`. **Schema changes are migrations**: add a file to `database/migrations/` (name it `<timestamp>-<what>.js`, export `up({ context })` and `down({ context })`, where `context` is the queryInterface). `database/migrator.js` (umzug) applies them in filename order and records them in `SequelizeMeta`. The baseline migration is deliberately irreversible (its `down` throws) and skips tables that already exist, so databases created before migrations existed adopt them without data loss. Never edit a migration that has been applied anywhere; add a new one.

**Migrations must be resumable.** MySQL cannot roll back schema changes (DDL is not transactional), so a migration that dies half way (a bad row, a crash, a restart) leaves the table half changed, and a migration that blindly re-adds its columns then fails forever with "Duplicate column name", which crashes every dev boot because `AUTO_MIGRATE` runs it again. Guard every step with the checks in `database/migrationHelpers.js` (`addColumnIfMissing`, `addIndexIfMissing`, `addConstraintIfMissing`, `tableExists`), make backfills only touch rows that were not done yet, and keep them repeatable. `tests/migrations.test.js` has an interrupted-migration test to copy.

Note: the existing user controller file is named `controllers/userContoller.js` (missing an "r") — match that exact filename when importing from it, don't "fix" the typo without updating the corresponding import in `routes/userRoutes.js`.
